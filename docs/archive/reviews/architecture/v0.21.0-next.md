## Confirmed findings

### ARCH-POST021-1 — standalone self-annotation withdrawal has no durable recovery

**Must fix.** `internal/server/sessions.go:341–369` builds `input` with an annotation-scoped
request ID for assignment admission, then sends the original id-less `msg` when no assignment
owns the conversation. `runtime.messageTransitionReason` returns immediately for an empty ID.
Consequently the ordinary held-message withdrawal has no receipt to release or retain until
the browser acknowledges durable draft restoration.

Normal condition: send a self annotation to a busy standalone agent, withdraw it, then lose the
HTTP response or fail browser draft persistence; alternatively, Stop while that input is held.
The queued input vanishes from GET recovery;
replaying the original annotation command merely acknowledges its already-accepted annotation
receipt and does not recover that input. FS-13.R37, FS-03.R100 and TS-03.R74 require the ordinary
input recovery behavior. TS-03.R78's explicit assignment receipt coverage left this separate
consumer unprotected. The durable annotation card still holds the instruction for manual
reconstruction; the probe establishes loss of managed recovery, not deletion of all source bytes.

The [HTTP/runtime/store probe](v0.21.0-next-input-repro.go.txt) fails in the independent reviewer
and parent runs: held and withdrawn messages have empty `request_id`, `AttachmentRecovery`
returns `state: not found`, and the unacknowledged later GET is empty. Preserve a stable input
receipt through the standalone delivery path as ordinary prompts do. Add a regression for
unacknowledged withdrawal; audit uncertain Steer through the same seam without assuming it has
already been reproduced.

### ARCH-POST021-2 — release assembly selects a retired hosted runner

**Must fix.** `.github/workflows/release.yml:17` selects `macos-14`. The handoff already carried
this release-preparation issue, but it had no finding ID. It is normalized here, not counted as a
newly discovered runtime defect. [GitHub's official retirement announcement](https://github.blog/changelog/2026-10-01-github-actions-macos-14-runner-image-retirement/)
states removal on 2026-11-02 and identifies supported replacements, including `macos-15`.
Its [runner-images inventory](https://github.com/actions/runner-images), checked 2026-11-06,
also reports all macOS 14 images retired from GitHub Actions.

A normal next tag or manual release cannot obtain its configured runner to assemble and verify
the archive (TS-06.R13–R14/R21; workflow §16). Select an available arm64 Mac image, preserve the
architecture assertion, and verify its packaging/toolchain assumptions. This review did not
trigger a release or a hosted job; the consequence follows from the configured label and the
runner owner's published retirement, rather than a newly observed CI run. The pending operator
decision stays visible in the handoff.

### ARCH-POST021-3 — installed operator guidance falsely describes a read-only viewer

**Must fix.** `internal/agentknowledge/operating-chuck/references/operate-agents.md:10` says the
viewer does not write files and that saved tabs retain positions rather than contents. The
categorical write denial is false after FS-03.R111; R112 also establishes a deliberate
browser-local draft-content exception to descriptor-only storage. A normal agent answering
whether Chuck can edit a linked file receives release-managed guidance denying the shipped task.

FS-18.R1/R3/R5 and TS-11.R1/R8 require release-matched interface detail in this canonical reference
(INV §10). Existing byte-identical publication tests pass: they faithfully distribute the stale
claim. Correct this reference to explain deliberate desktop text Save, the separate draft/recovery
exception, and retained phone/read-only restrictions, without implying a new agent-tool authority.
No new knowledge system or exhaustive manual is needed.

### ARCH-POST021-4 — an older refresh can replace the successfully saved view

**Worth fixing.** `ui/src/features/fileTabs/useFileFreshness.ts:67–78` checks lifecycle validity
after an asynchronous refresh, but not whether another operation applied a newer snapshot while
it was pending. `FileViewer.tsx:367` applies the successful Save and ends editing. An older
refresh that then resolves is unblocked and overwrites that view. The candidate-base fence at
lines 27–30 only protects refreshes that were already buffered while blocked.

Normal schedule: edit while an external revision settles; its refresh read starts; adopt/recheck
that external base and save; resolve the older read afterward. The reader shows pre-save bytes
despite successful Save (FS-03.R111; TS-08.R153–R154). Disk bytes remain safe; another poll normally
repairs the temporary false display. No disk-loss or live HTML side effect was demonstrated.

The [real-hook schedule probe](v0.21.0-next-freshness-repro.tsx.txt) fails in reviewer and parent
runs: `apply` receives `reviewed-external` after the supplied current snapshot becomes `saved`.
Fence read completion against a snapshot generation captured before that read; cover this schedule
without introducing another refresh mechanism.
