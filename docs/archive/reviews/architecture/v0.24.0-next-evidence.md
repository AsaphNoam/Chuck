## Confirmed counterexamples

### ARCH-EDIT-CONTEXT-1: replaced context returns through a frozen bridge

Normal use: send the first message, switch backends, then edit that message. Promise: the new
provider starts from the conversation's original startup context and sees the replacement, with
the original turn omitted (FS-01.R61, TS-04.R113, TS-02.R70).

Authority crosses two artifacts: the active transcript fold and the frozen startup snapshot.
`internal/server/switch.go:250` builds `HistoryPrimer` from the visible conversation;
`internal/server/edit.go:504` composes its first-message candidate from the latest snapshot;
`internal/runtime/runtime.go:163` appends that bridge to the new process's system prompt. The
first-message path has no preceding native turn to reject the switched lineage. Its local fold
is correct while the provider receives the superseded message and reply.

The retained [Go probe](v0.24.0-next-edit-primer-repro.go.txt) uses existing server fixtures and
real SQLite, HTTP and fake-ACP subprocesses. It performs Claude → Codex → Claude, edits the first
message, proves the active transcript has exactly the replacement, then reads the actual final
`session/new` request. It fails twice; the sanitized second run reports:

```text
first-message Edit hides the old turn in active history but resends startup context:
old_prompt_present=true old_reply_present=true
```

The first failure took 3.56s; the sanitized reproduction took 6.04s. This proves incorrect startup
bytes handed to the provider interface, without claiming credentialed provider behavior. An
existing first-message control with no switch passes alone (0.814s) and in the focused Edit suite.
It failed once when combined with the negative probe (`active prompts = []`); its settled-record
poll can finish before replacement dispatch. That timing-sensitive test limit remains disclosed.

The repair must preserve genuine original context, including a legitimate clone/initial bridge;
blanket removal of every primer is not an established fix. Recover/prove its pre-message origin
or refuse visibly before acceptance. Retain a startup-wire regression and cover the other backend.

### ARCH-REVISION-1: reconnect retains superseded phone pages

Normal use: read older phone history, disconnect, Edit on desktop, reconnect. Promise: reconnect
replaces the active view from the committed revision; a cursor cannot retain the replaced reply
(TS-03.R91, TS-02.R70, FS-01.R61).

`ui/src/remote/connection.ts:319` hydrates `history_revision` but advances only `transcriptRev`;
the separate `revisionEpoch` advances only on the live revision event at line 372.
`ui/src/remote/AgentScreen.tsx:401` retains older pages and its anchor, and line 429 joins those
pages to the new tail without comparing revisions. The first old tail event is itself retained
in the earlier-page cache. A superseded user message and reply can therefore coexist with the
replacement after the phone misses that event.

The retained [component/stream probe patch](v0.24.0-next-phone-reconnect-repro.patch.txt) extends
the existing stream fixture. A full 750-event initial window makes the last user message land
on the preceding page. After loading it, the server's revised responses contain only the active
revision marker, replacement and reply. Rehydration supplies `history_revision: 1` without the
missed live event. The revised reply renders, but the assertion that the superseded user text is
absent fails. The same probe driven by the live revision event passes. The complete probe file
has three passes and this single failure (1.71s); existing stream tests stay intact.

This is deterministic React/MSW/serialized-stream evidence, not a physical phone, rendered
geometry or real network-disconnect receipt. It isolates the client cache owner after an honest
missed event. Repair revision reconciliation for cached pages and pending reads, including an
Edit during hydration/backgrounding.
