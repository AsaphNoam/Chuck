## ARCH-1 — Offline repair treats PID-file inspection errors as proof of absence

`internal/cli/reindex.go:14–19` returns false for every `readPidfile` error; the caller then opens
the separate repair writer and can report full success while the dashboard is live. A malformed
or unreadable PID file is an environmental fault, rather than the ordinary healthy case. The
failure removes the offline guard when its input is untrustworthy. This creates an opportunity
for concurrent live indexing and repair; it is not demonstrated data loss. TS-02.R2/R58 and
INV §7/§9 describe the affected offline/writer boundary.

An isolated real-process probe used the source-built tagged binary, disposable home
`/private/tmp/chuck-pidfile-proof-home` and loopback port 46137. With a healthy PID file,
`reindex` exited 1 and required stopping the server. With malformed JSON in `dashboard.pid`,
it exited 0 and printed `reindexed archive` while `/api/health` still returned 200. Repeating
with file mode `000` produced the same successful concurrent invocation. Both owned dashboards
were stopped through their process handles; health was unreachable afterward. The home contained
no conversations, so this proves the refusal gap only.

To reproduce: start the audited binary with a fresh `CHUCK_HOME` on a loopback port; verify health
and healthy-file refusal; overwrite only that disposable home's `dashboard.pid` with malformed
JSON, or chmod it to `000`; repeat reindex and health. Never use an operator's real home for this
probe. Restore file permissions and stop the owned foreground process through its handle.

The small repair is to distinguish a genuinely absent PID file or a proven dead PID from a
read/decode failure, refuse repair with an actionable inspection error in the latter case, and
retain healthy/stale-PID behavior. Exercise CLI refusal before opening the repair writer,
including malformed and unreadable files. This does not require a new locking mechanism.
TS-02.R58 explicitly disclaims stronger exclusion than the existing guard; concurrent startup's
check/write window is a coverage limit, not another finding.
