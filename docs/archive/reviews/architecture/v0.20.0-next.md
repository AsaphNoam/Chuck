## Confirmed findings and independent probes

### ARCH-NEXT-1 — late MCP initialization outlives revoke

`internal/messaging/messaging.go:335–359` calls the SDK handler before recording the response's
session ID under its launch token. Revocation during that call sees no owned session; subsequent
tracking sees no registered token and returns. The SDK's configured zero session timeout leaves
that session retained. Token authority is still refused; this finding establishes retention, not
unauthorized tool access. TS-04.R7 and INV §4/§5/§16 require cleanup.

The [reproducer](v0.20.0-next-mcp-repro.go.txt) pauses the real SDK HTTP initialize response after
session creation, revokes the launch, then releases the response. It fails 3/3, plus one independent
parent repeat: `revoked launch retains initialized SDK session ... (HTTP 200)`.
Existing `TestRevokeReleasesOnlyItsMCPSessions -count=3` passes and covers completed initialization.

### ARCH-NEXT-2 — moved input loses stable receipt and attachment provenance

`internal/state/attachment_receipts.go:130` rewrites the receipt's `(agent_id, request_id)` key
and clears its assignment before attachment copying. `SourceAgentID` is only returned in memory.
The original HTTP endpoint's replay lookup consequently misses the accepted command. Interrupting
between that transaction and copying leaves no persisted attachment source after recovery.
TS-09.R69 and INV §5/§9/§15 require stable acceptance identity and recoverability.

The [store probe](v0.20.0-next-input-store-repro.go.txt) confirms the original receipt disappears.
The [HTTP/startup probes](v0.20.0-next-input-replay-repro.go.txt) confirm:

- Original accepted input moves to a successor; retrying the same original HTTP POST emits a
  second fake-provider `session/prompt`: `got 2 total prompts, want 1`.
- Simulated interruption immediately after the claim, followed by actual
  `ReleaseRestartedAttachments` and `recoverAttachmentStorage`, produces a released recovery
  receipt with `source=""`; opening its attachment under the successor fails.

These exercise real stores, HTTP and runtime transport, with assignment movement staged directly.
The interruption probe executes startup recovery seams; it is not an OS kill/reopen or live-provider
replacement receipt. Original bytes may remain under the former owner, but the accepted recovery
record lacks the source needed to use them. Preserve that distinction from proven byte deletion.

### ARCH-NEXT-3 — unusable native resume double charges recovery

`internal/pipeline/decisions.go:272–275` passes through two charged operations: interrupted retry
at `internal/state/pipeline_tasks.go:1050`, then replacement at `:1091` when that start is parked.
TS-09.R70 explicitly requires successful replacement within the same recovery operation not to
charge again. INV §5/§15 apply to the durable operation identity.

The [controller/store probe](v0.20.0-next-recovery-repro.go.txt) starts with two rounds used,
recovers an interruption, stages native unavailability through the normal parked-task seam, and
requests replacement. It fails with `ok=false ... state=paused attention=recovery_exhausted rounds=3`,
before useful successor execution. It simulates native refusal; no credentialed native failure
was induced.

### ARCH-NEXT-4 — embedded knowledge still denies run checkout isolation

`internal/agentknowledge/operating-chuck/references/operate-agents.md:32` says everything in one
project, including pipeline stages, shares a checkout and parallel isolation requires another
project. The pipeline reference gives no exception. FS-19.R12 and TS-09.R61–63 expressly permit
an owned run checkout within the existing project, with recursive placement and frozen lifecycle.
FS-18.R1/R3/R5, TS-11.R1 and INV §10 require matching operating guidance. An agent answering how
to run isolated pipelines receives false advice; this is an installed knowledge boundary, not
a runtime placement failure. Correct the canonical linked references without adding another manual.
Full `internal/agentknowledge` tests pass, including byte-identical publication into both provider
views; publication fidelity does not establish semantic currency.
